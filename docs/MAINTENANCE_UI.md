# Maintenance interface

The opt-in console is served at `/` by the existing persistent Navigatorr HTTP process; MCP stays at `/mcp`. It uses the same SQLite actions, profiles, permissions and HTTP transcode worker. No separate project, frontend build or second workflow implementation is needed.

## Enable

Add to the configuration used by the persistent server:

```yaml
mcp:
  transport: streamable-http
  listen: "127.0.0.1:8098"
web:
  enabled: true
  auth_mode: cloudflare_access
  cloudflare_access:
    team_domain: "https://your-team.cloudflareaccess.com"
    audience: "your-access-application-aud"
```

Cloudflare Access handles Google sign-in and registration policies. Configure its application to protect the whole origin, including `/api/maintenance/*` and `/mcp`. Navigatorr verifies the Access assertion signature, issuer, application audience and expiry using the team's public keys; it does not present a second login, ask for a token or offer local sign-out in this mode. The team domain and audience are server configuration, not credentials the browser user enters. Use HTTPS and keep the origin private behind the proxy/tunnel. Existing MCP authentication is unchanged.

For standalone use, omit `auth_mode` (defaults to `token`) and configure exactly one of `web.token_file` or `web.token` with a random token of at least 24 characters. This mode retains bounded 12-hour HttpOnly/SameSite sessions.

To reach the same token-mode console both privately (LAN, VPN) and through Cloudflare Access, keep `auth_mode: token` and also set `web.cloudflare_access.team_domain` and `audience`. A request carrying a valid Access assertion for that audience is then signed in without the token form and without a local sign-out. Every other request still needs the token. The assertion is verified the same way as in `cloudflare_access` mode, so a forged or foreign header only falls back to the token check. Both modes preserve same-origin mutation checks; worker credentials and \*arr keys stay on the server. `web.enabled` defaults to false and requires `streamable-http`. Enabling the console does not enable destructive actions or audio-only transcoding. The SQLite migration is automatic (schema 8).

## Mobile and PWA

The mobile view opens on the queue, with fixed bottom navigation, compact savings and job telemetry, 44-pixel controls on touch-sized layouts (including landscape/tablet), 36-pixel desktop controls and safe-area spacing. Typography and spacing are deliberately dense: 13-pixel job titles, inline source/scope/profile rows and a single-line worker status/percentage. The original paper/forest colors and serif headings are retained. Zero-valued batch counters and redundant workflow steps move to detail; full source paths remain in job detail. Progress bars span the full job row and dialog actions keep content-sized widths. File selection remains directly available in **Files**, and less common profile controls open in a typed settings dialog. Returning to the foreground refreshes monitoring without discarding the current prepared conversion. The browser is not the transcoding worker: backgrounding or closing the PWA leaves durable jobs on the server.

On single-column widths (900 pixels and below, including phone landscape), Files has two steps: browse/select, then configure the transcode. Tapping a file advances directly; marked files use Continue, and Use folder configures the current folder. Back retains the prepared settings and selection. Wider desktop layouts keep the browser and form together. File checkboxes use a 14-pixel visual inside the same generous hit area and alignment column as folder icons. Open a path sits beside optional search in the source toolbar.

Several files can be ticked at once, in the folder browser and in a series. Dragging down or up the checkbox column ticks every file the pointer crosses (or unticks them, when the drag starts on a ticked file); it works with a finger and a mouse, a row the pointer leaves goes back to how it was, and a tap or click that does not reach another row still toggles just that file. A finger that starts on a checkbox draws the range instead of scrolling the list; start anywhere else on the row to scroll. Shift+click ticks everything between the last file ticked and the one clicked, and Shift+↑/↓ on a focused checkbox grows or shrinks a range from the row it started on. **Select range**, a button under the column header that appears once a file is ticked, does the same as Shift+click for screens with no Shift key: it arms the next tap, which then ticks every file from the last one ticked to that one (the button turns into **Cancel range** until then). A short hint above the list teaches the drag, and the Shift keys on devices with a pointer. Folder rows are never part of a range, and a plain click already toggles a single file, so there is no separate Cmd/Ctrl+click.

The same origin exposes a standalone manifest, maskable 192/512 icons, an Apple touch icon and an **Install** button. Android browsers can offer their installation prompt; iPhone/iPad use Share → Add to Home Screen. Installation requires HTTPS (localhost is sufficient for development). A plain HTTP LAN address can still use the web interface, but does not provide the secure context required for the service worker.

The versioned service worker caches only the public HTML/CSS/JS/icons. API responses, sessions, tokens, job history and mutation requests are never cached or replayed. With the server unreachable, a previously visited PWA can reopen its shell; it displays a disconnection notice and requires reconnection for job data or changes. In an already-open page, the last visible measurements are marked stale and mutation controls are disabled. The page automatically retries every five seconds; browser online/foreground events also revalidate the server/session. An uncertain submission keeps its existing durable receipt; reconnection does not automatically resubmit it. The public shell falls back to cache on network failure, proxy 5xx or a five-second network timeout; cache-write failure still permits the live response. Asset changes update the worker and retire only Navigatorr's old shell cache. Expired sessions dismiss stale approval/detail dialogs. Cloudflare mode directs the user to reload for Access authentication; standalone mode exposes its token sign-in.

## Workflow

- Browse configured filesystem read roots directly. File sizes come from disk; folder navigation with clickable breadcrumbs and continuous loading work without Sonarr/Radarr. Search is optional behind its icon. Optional Series/Movies catalogs add metadata and library import associations, rather than defining the transcode source.
- Files rows carry one small mark after the name when a conversion batch has handled that file, so a long session does not lose track of what was already added. The mark is `nav_status` on library titles, season groups, episode/movie files and folder entries (`/api/maintenance/library` and `/folder`): `queued` (dashed ring), `working` (small spinner, still under reduced motion), `attention` (amber `!`, a decision is waiting), `converted` (outlined `✓`, a candidate exists and the original is untouched), `replaced` (filled `✓`, the library file was swapped), `kept` (`–`, checked and left as it was) and `failed` (a faint `↺`; the file itself is fine, only its conversion did not finish, so it is the quietest mark). A folder, title or season shows the state most worth looking at among its files, with how many files are in that state, and its tooltip lists every state (`2 converting · 3 queued · 1 converted`). That order is attention, working, queued, converted, replaced, kept, failed: a converted copy that still waits for a replacement outranks one already replaced, and a failed conversion never hides anything else, including a later success of the same file. States come from the batch ledger (`transcode_batch_items`, the child `transcode_media` action and its `promote_transcode_candidate` replacement). Previews (dry runs), cancelled items and the unfinished leftovers of an ended batch show nothing, and a file converted only through a direct MCP call, outside a batch, is not marked. Library rows are matched by the *arr's own file path, the one a batch is created from and stores after resolving it, so a library that reaches its files through a symlink shows no marks until the path matches. The server reads the ledger once for all rows of a page and keeps what it read: for three seconds (longer when the read is slow, so it never takes more than a tenth of the store's time) the copy is used as it is, up to a minute it is shown at once while a single read refreshes it in the background, and any change made through the console (a POST) drops it so a retry shows immediately, and the page re-reads the visible rows when Files opens and about every ten seconds while it stays open, changing only the marks that moved.
- Select a single file, marked videos, the videos in a folder, or its subfolders. Filesystem batch admission freezes an explicit `paths` list (up to 1000 videos), resolves allowed roots and deduplicates canonical paths. An oversized selection fails instead of silently truncating. Series catalogs also support a season, whole series and selected-file intersection, including shared multi-episode files encoded once.
- Use a shared recipe, automatic selection or a per-job typed profile. The form covers x265 and VideoToolbox quality/bitrate, audio copy/compact, final validation, bit-depth preservation and size guardrails. A profile with optimization enabled is refused for new jobs: choose a goal instead. Profiles exposes less common fields in a typed settings form; editing a shared profile preserves fields that are not changed.
- **Size budget.** Under *Save space* an optional budget caps the finished size: a percentage of the source (5 to 85), a number of gigabytes (at least 0.05), or *Match sibling episodes* with a multiplier (1.0 to 4.0, default 1.5). *Change goal* shows and edits the budget a file was frozen with; job detail shows the budget against the result, a small rate-quality chart and, for a candidate below the normal quality target, the label *Below quality target — within size budget*. When the media engine encodes the budget and the result measures below the quality floor, no candidate is offered and the job shows **Try with x265**, which starts a new job with the same settings and the media engine off. See [transcode/TRANSCODE_AUTOMATIC.md](transcode/TRANSCODE_AUTOMATIC.md).
- **Process videos** starts from a goal (smaller files, quality, HEVC). Profiles, custom settings and batch limits sit in the collapsible **Advanced: technical profiles** section; its summary shows On/Off. While a technical profile is on, the goal stays visible but disabled and marked *Goal not used*, because the chosen profile replaces it on submission.
- Cleaning a podcast episode is not offered in the page: Activity opens with the queue and nothing else. The page no longer starts podcast cleaning; podcast jobs that exist still show in the queue and in the worker slots, which label them *Podcast slot N*.
- Preview a batch or enqueue a conversion. Admission returns immediately after the action and retry receipt are committed; the process-owned reconciler performs preflight and execution. Closing the browser has no effect. Restarting Navigatorr recovers pending actions. Repeating the same receipt, even after completion, returns the original action; changing its inputs is rejected.
- Files, Queue, Profiles, Stats and Settings are separate workspaces. Queue and filesystem listings load continuously with a fallback continuation button. UI and MCP jobs expose inline retry, batch pause/resume, decisions and cancellation. Pausing stops new admission; admitted jobs continue. Cancellation propagates to children. Batch details show paginated native file rows and their child jobs, rather than requiring JSON inspection.
- Terminal batches with failed or cancelled files offer Reconfigure. The read-only form restores the frozen failed/cancelled subset and original settings, including custom profiles; completed candidates stay in the previous history. A new attempt requires explicit submission and fresh worker admission. Identical submission receipts prevent duplicates after a lost response. Changed encoding settings start a new job; old estimates are not assumed valid. Savings-gate failures are grouped by cause in the queue, with individual estimated growth/savings in file details. Processed counts include failures and skips, rather than implying successful conversion; failed processing and skipped replacement have distinct stages.
- A standalone single-file `transcode_media` job (or an older `benchmark_transcode` one) that was cancelled, or completed without a winner (`no_suitable_candidate`, `quality_not_met`, `size_budget_exceeded`, or `search_budget_exhausted` from the removed sample search), offers **Run again** on its row and in the detail dialog. It is not offered for jobs with a candidate, jobs waiting for a decision, batch children (which keep **Change goal**), jobs with a replacement, or sources the worker cannot handle. A confirmation names the file and goal, says **Originals stay in place** when the job did not ask to replace the original, and, when the same source already had two or more rounds without a result, says so ("This file already had N rounds without a result"); confirming is the explicit decision for another round, and nothing is ever retried automatically. `POST /api/maintenance/rerun` (`{id, key}`) re-checks eligibility, copies the original inputs minus the idempotency key into a **new** action under the caller's fresh key (the earlier job's key is refused), requires a ready worker like Retry, refuses (409) while another action of the same kind is active for the same source, and refuses a job that has a candidate or replacement. The confirmation dialog keeps one key, so a lost response followed by another click replays the same key and returns the same action instead of a second job. When `replace_original` was set, the confirmation says the original is replaced only after review and approval. The earlier action is never resumed or changed. The job list carries a `rerun` summary (`source_path`, `mode`, `replace_original`, `no_winner_rounds`) only on eligible jobs.
- **Try again** is how a file is saved after its encode finished and only saving it failed (the media share was unreachable, say). The file's batch row and job card say one thing, whatever the storage error was: "Encoding finished, but the file could not be saved. The encoded copy is kept." *Change goal* is hidden for it, and the server refuses a goal change for such a file with the same explanation, because it would encode the file again. **Try again** sends `action_resume` with the decision `recheck` to the file's own job, needs its worker like Retry, and asks no confirmation, since nothing is replaced. The coordinator asks the worker to publish the finished candidate again (`POST /v1/jobs/{id}/retry-publication`, see the worker API in [transcode/RFC_PERSISTENT_TRANSCODE_DAEMON.md](transcode/RFC_PERSISTENT_TRANSCODE_DAEMON.md)); no encode starts and no setting changes. A worker that predates the route leaves the file waiting and the reason says to update it. The batch-items rows carry `waiting_decisions` (the decisions the file's attempt offers) so the page can tell this state from other waits.
- **Show in Files** takes a failed, cancelled or skipped file back to where it lives: the Files tab opens on the media folder, the file's own folder and the file, with the goal form ready to choose another goal or try again (`?view=files&source=folder:<root>&folder=<dir>&file=<path>`, the same address a shared link would use). It appears on batch rows in those states and on the job card of a failed or cancelled job, and in the open detail of any finished one; it only navigates, so a busy batch does not disable it. It is absent for previews and for a file outside every media folder. A cancelled *replacement* cannot be resumed in place, since the replacement of a candidate runs once per candidate; convert the file again from Files.
- **Pause all (worker drain)** is the one switch for deploying a worker safely. The Queue toolbar has three equal tools: the status filter (an icon that lights green while a filter is chosen), **Pause all** (a pause icon that turns into a green *Resume* button while paused) and Refresh. Under the title a status line says *Running*, *Pausing — N still encoding, M waiting for a turn on a worker* (amber; the second count is files a worker has accepted but not started) or *Paused — ready to deploy*, with how many files are held back. The same state shows in the worker dialog and in the header's worker status. While drain is on, nothing new is sent to a worker: batch files wait, new conversions and podcast submissions are held as *Waiting for a worker deploy*, and the worker holds its own queue too (`/v1/hold`, kept in its state directory), so a file it accepted but has not started stays queued; only encodes already running finish and are saved. The server checks the hold on every worker check and reconciler tick, re-sending it to a worker that lost it and lifting it from one that kept it after a Resume it missed (`GET /v1/hold` shows `hold` and how many jobs the worker is running; rolling the server back to a version that does not know the hold leaves a held worker held until it is lifted with `PUT /v1/hold {"hold": false}`). A queued file on a worker that confirmed the hold counts as held back and does not block a deploy, unless the worker runs more jobs than the database shows encoding; a worker that predates the hold keeps starting its queue, so its queued files still count as in flight. Drain does not touch paused batches and Resume does not resume them; it only lets held work go. *Ready to deploy* needs drain on, a 15 second settle window, every worker reachable, no job running and no encode waiting to be saved (*Try again*, or cancel it). The dialog lists what still blocks it, file by file, with **Show in Files** on each. State lives in the server's database (migration `worker_drain`), so a restart keeps it. `GET /api/maintenance/worker-drain` reads it and `POST` with `{"enabled": true|false}` changes it (same-origin header required); the MCP tool `worker_drain` does the same, and the status is also in `/api/maintenance/workers` and `worker_health`.
- The queue has one stable order: newest workflow first, by its number, whatever its state. A workflow that needs a decision keeps its place and shows the amber `!` chip; the **Needs decision** filter and its count list them together. Resolving or finishing a workflow never moves the others.
- **Worker slots.** The slots sit between the queue header and the job list. Their heading reads *Worker slots · used/total occupied* (with *N of M nodes unavailable* when a worker does not report), followed by a chip with the scheduler's health (*Normal* green, *Degraded* amber, *Unknown* grey, with the age of the observation) and a gear that opens the node's slot settings. Phones (900px and narrower) get one row per node that opens onto its slots: the row shows a status dot, the node, `used/total` (or `0/1 · all available`) and, when the node splits slots, `Video 1/1 · Podcast 0/1`. A node opens by itself while something runs on it or it is down, stays shut while it is idle, and keeps whatever a person opens or shuts through the refreshes. A free slot is one line (*Video slot 1 · Available*); a busy one is the file, the phase with its bar and percentage, and one line of facts: the encoder and rate (`x265 CRF 22 · 4.94×`) or a short note while waiting, then the kind (*Full conversion · x265*, *Full conversion · VideoToolbox* when the job's encode is known, or *Podcast processing*) and the elapsed time. A quiet heartbeat turns that line amber (*No recent worker heartbeat*). A node that does not report keeps its row, red, with the reason, and nothing to open. Wider screens get a table of only the slots that are running (Slot, File, Phase, Progress, Kind (with the encoder), Elapsed; the phase's name has the encoder and speed (or a short note) under it, and the bar has a column of its own so every bar starts and ends in the same place) with the free slots counted in one line underneath (`1 slot available · node-b 1`) and unavailable nodes listed in red. Both layouts are rendered from the same worker report, and the stylesheet picks one. The full text of a line is in its tooltip. The encoder and speed come from the worker's activity and are put together by the server, so they show for any worker version.
- **Queue row layout.** Each job is a quiet row: the number, the title as a real link to the job (`?view=queue&job=<id>`, so a middle click or copied link works and a plain click opens the dialog in place), one status badge and, for a batch that is not itself waiting on a decision, a small flag when something needs review. A batch of chosen files is named from where they are: the folder when they share one, the folder that holds them all when they sit in its subfolders (a movie with an extras folder, a show's seasons) as long as that folder is inside a library and not the library itself, otherwise the start of their file names (the series), otherwise the first file and how many come with it; a single file is named by its file name, and never "Selected files" while a better name is known. Under the title is one sentence saying what happened or what is next (*3 candidates ready · Originals unchanged*, *Worker cannot access media storage…*), and the single next action is a link at the end of that sentence (*Review ›*, *Retry ›*). The other actions are icon buttons at the row's corner: up to three stay in view (Pause or Resume, Cancel, Archive, Stop batch · keep originals, ranked in that order, Cancel and Stop in red), and when there are more the rest go into one `⋯` menu that closes after a choice; a row never shows a second labelled button. A facts line follows with the kind and sizes (*Batch · 9.00 GB source · 3.00 GB potential savings*) and is left out when it would only repeat the kind. A batch shows one segmented bar per file (done, failed, running, needs you, skipped, cancelled, waiting) with a legend (`3 done · 2 running · 7 waiting`); a single running file draws its measured progress as the same 6px bar, with the percentage at the right. On phones the title takes the whole line beside the number (two lines before it is cut), the status badge sits under it, and the corner buttons are centred on the title's first line. Bars stop at 560px on wide screens and never leave blank space under the legend. Raw tool errors become short sentences (*Couldn't read the video file*). Rows are one column on every screen width, with the bar across the full row, so a row with more to say grows by a line or two rather than by a column. A running batch folds the legend and the percentage into one line and the current file, its time and the files left into one more, so it takes four lines under the title at most; a single running file shows its heartbeat on one line.
- Queue rows use one status and a concise type/result summary, with known source/candidate sizes and savings. Failed jobs show a shortened error reason when available. Decision rows show the next action instead of stale worker speed or progress. Worker measurements refresh every five seconds while the page is visible: phase, percentage, queue position, speed, fps and stale-observation markers. A worker slot row shows its job in the same green as a batch row: the measured encode percentage on a determinate bar, and while no percentage exists (waiting, preparing, analysing, or the first pass of a two-pass encode) a short phase label with a slow sweep instead of a number, so it never shows an old 100% from the previous encode. A slot whose heartbeat has gone quiet turns muted and still, and says so. A batch row that needs a decision keeps its single status badge and adds a small amber `!` chip on the title line rather than a second badge row. Queue telemetry appears only during active execution or worker waits. ETA is an approximation only during encoding with recent progress, source duration and measured speed. Process-owned reconciliation remains authoritative; browser polling neither starts nor owns encoding.
- Job detail renders the server's result summary (`benchmark`, a key that keeps its historical name) as a result card: outcome, message, size warning, the failed checks with measured value and limit, and the next step. Jobs from the removed sample search keep their stored card. A quality/size job that produced no candidate shows **Skipped**, not Completed. Engine reason codes are translated, with the raw text kept under **Technical details**. Every waiting decision other than pause, resume and retry opens a confirmation first. The next step uses the plain-language `user_next_step`; `next_step` stays agent guidance for MCP. During the full encode, job and batch rows show a smoothed remaining time from ffmpeg progress (`~1 h 10 min left`, and for batches `about N files left`); it is hidden when speed is unknown or progress is stale. Nothing is chosen automatically. Before/after captures: [`screenshots/ux-review/`](maintenance-ui/screenshots/ux-review/).
- **Settings → Appearance** switches between System, Light and Dark. The choice is stored per browser (`localStorage`, key `navigatorr-theme`) and applied by `/theme.js` before first paint; without storage the page follows the system. All colors are CSS tokens on `:root` with a dark palette for `prefers-color-scheme: dark` and for a pinned Dark choice; `theme_test.mjs` checks that text, badges and status colors meet WCAG AA in both palettes. Browser chrome uses per-scheme `theme-color`. On touch screens form text is 16px (no iOS zoom on focus), small text controls get a 44px hit area, and wide tables scroll inside their panel. Captures: [`screenshots/theme/`](maintenance-ui/screenshots/theme/).
- The dedicated **Stats** section distinguishes estimates (a goal's size estimate or profile heuristic), validated candidate savings, and completed replacement savings. The persistent action ledger supplies cumulative net content bytes and a chronological trace; batches and duplicate replacement claims are not counted twice. Originals and retained recovery copies exclude a job from realized savings. The figure is file-content reduction, not a measurement of filesystem free space or allocation.
- Conversion produces a candidate. A separate replacement action reviews its exact paths and requires approval before mutation, retaining verified recovery on uncertain outcomes. Import routing comes from the admitted job or parent batch; historical jobs without that context offer an explicit replacement method. Existing replacement actions are reopened, and consumed candidates are no longer offered for replacement.

  **One approval per file.** *Replace file* creates the replacement action and opens its review at once (a pending state while the original and candidate are verified), then shows the exact paths, sizes, savings and method; the single *Replace file* button in that dialog is the only approval. There is no separate "Review replacement" step after it. Accepting a candidate that failed validation offers *Accept and replace*, which leads to the same one review (*Accept only* keeps the decision for later). A batch is approved only against its replacement plan, never through a generic dialog. The server enforces what the person saw: a single-file approval must carry `plan_digest`, a SHA-256 over the service, library IDs, both paths, both file hashes and both sizes of the reviewed plan. A missing or stale digest leaves the job waiting for a decision with nothing changed, on every surface including the `action_resume` tool (`plan_digest` argument; the compact promotion summary exposes the current digest). Promotions that belong to a batch are bound by the batch digest instead. Destructive gating, idempotency keys and series claims are unchanged.

  **Recovery and verification cost.** A promotion preserves the original by renaming it aside right before the library file is removed (`move_aside`, no bytes copied) and falls back to a verified recovery copy (`copy`: copy, then a full SHA-256 read-back) only when something rules the rename out. `recovery_mode_reason` on the promotion records which: `original_moves_aside`, `copy_forced`, `no_stable_identity_for_the_original`, `earlier_recovery_file_present`, `mount_probe_failed`, `move_aside_refused` (the rename was refused and a copy followed) or `recorded_before_the_mode_existed`. For `mount_probe_failed`, `recovery_mode_detail` says which probe step failed (`create_file`, `stat`, `identity_unstable_while_unchanged`, `rename_no_replace`, `rename_changed_identity`, `rewrite_in_place`, `rewrite_changed_identity` or `rewrite_kept_change_time`), the filesystem type of the recovery directory and what was observed, never a path. A probe error that says nothing about the mount (such as an unwritable directory) is not cached, so the next promotion probes again. Whole-file hashes read 1 MiB chunks a few chunks ahead of the hash, so network round trips overlap with SHA-256; digests and every check are unchanged. Filesystem replacement uses the original basename with `.mkv`, refuses collisions and verifies the published file before recovery cleanup. Sonarr/Radarr remain optional library adoption integrations; existing series batch adoption keeps one exact batch approval.
- **Profiles** uses the existing managed recipe store, with revision checks, history and immutable admitted plans. **Settings** calls the configured recipe collection Shared presets: Refresh presets reloads its configured builtin/file/remote source, and Restore previous restores the preceding validated cache. The previous Reload and Update controls called the same operation and are now one action. These changes affect new jobs; admitted plans remain immutable. Verified recovery cleanup also uses normal controls. No generic JSON console is shown; the restricted MCP adapter remains available internally. Generic `call_api` and unrelated destructive filesystem tools are excluded.

## Boundaries and extension

`maintenanceui` owns HTTP/session handling, filesystem navigation, normalized optional catalog reads and embedded browser assets. `action` owns durable admission and workflow policy; `transcode` owns the worker protocol; recipe policy remains typed and versioned. The UI is an adapter over registered MCP handlers, so future maintenance operations can be deliberately exposed without cloning policy.

Audio streams inside videos retain the existing copy/compact support. Audio-only files remain a later feature: introduce a typed audio plan/recipe and executor validation in the domain first, then add its controls/navigation in this adapter. The current bootstrap explicitly advertises only `asset_kinds: [video]`.

Continuous library navigation uses bounded pages in the adapter (100 records maximum per page); Sonarr/Radarr still return their underlying collection to the server. Operations paginate after filtering the shared workflow ledger; batch items paginate independently. Savings history returns the latest 25 replacements while the total includes all verified records. Standalone web sessions are process-local, so a server restart requires signing in again while jobs continue. Cloudflare Access sessions remain managed by Cloudflare across Navigatorr restarts.

## Validation

Backend regressions cover durable admission/restart/cancel/retry receipts, authenticated same-origin requests, restricted tools, bounded library reads, selected-file/season and filesystem filtering, worker log errors, filesystem/Radarr approval/recovery/identity drift, savings accounting/restart and UI response-race regressions. Existing Sonarr promotion and batch tests remain in the suite. Manual browser verification uses an isolated synthetic Sonarr/Radarr library and temporary database; it does not replace acceptance against a live NAS/worker.

Mobile browser checks cover 320, 360, 390 and 430-pixel widths, tablet (768), landscape (844×390), desktop (1280), file/profile selection, batch preview/details, inline retry, replacement-plan review, advanced controls and actual server-stop/offline reload/automatic recovery. PWA regressions cover public routes/icon dimensions, cache isolation, network-first fallback, mutation blocking and preservation of prepared inputs on reconnect. Installation and keyboard behavior on physical iOS/Android devices remain device acceptance checks.

### Layout verification

`maintenanceui/layout` opens the job detail in a real browser (Playwright) for every scenario in `fixtures.mjs` (each job kind and state: queued, analysing, encoding, verifying, saving, waiting for a decision, failed, cancelled, candidate ready/larger, batches that are running, mixed, replacing, replaced or failed) and checks the rules in `invariants.mjs` against computed boxes, not pixels: no control overlaps or leaves its container, nothing scrolls sideways, every tap target is at least 44 px, single-line text stays on one line, a bar and a spinner look the same everywhere, nothing is said twice, no font is under 12 px, the section order is fixed, and the header and action bar stay small and in view. Each scenario runs on seven screens (320 to 1280 wide, landscape included), in light and dark, at 150% zoom, and with short, long, unbroken and CJK names and tiny and huge sizes.

```bash
cd maintenanceui/layout && npm ci && npx playwright install chromium   # once
npm run verify                  # quick matrix, about a minute
npm run verify:full             # the whole product, several minutes
LAYOUT_ONLY=batch-replacing npm run verify
node inspect.mjs <scenario> [screen] [shot.png]   # one cell, with a picture
```

`out/report.md` lists each distinct finding with an example cell and `out/index.html` shows the pictures; `LAYOUT_BROWSER=chrome` uses the installed Chrome. The fixtures are synthetic and `out/` is not committed. A new job state or button gets a scenario in `fixtures.mjs` before it ships.

The [adversarial review](maintenance-ui/ADVERSARIAL_REVIEW.md) records the latest fixes, validation and remaining external acceptance checks. Deployment is cancelled.

## Design reference

The compact English interface follows the [Navigatorr Stitch project](https://stitch.withgoogle.com/projects/6967843794345897924): paper/forest theme, outline icon tabs and actions, icon-only refresh, no marketing header or duplicate queue, and structured profile controls. Generated examples are design references; savings and job states always come from the real ledger. Installation instructions appear only on request in a dismissible mobile dialog. Desktop installation is offered only after the browser emits its native installation event.

Queue and Profile actions use uniform icon controls with accessible names, differentiated primary/review/retry/cancel treatments, and shared desktop/touch dimensions. Mobile Profiles uses one native selector. Desktop checkboxes prepare the selected job immediately; successful encoding clears the submitted selection while retaining preferences.


### Process progress and retained copies

Batch bars retain the exact processed-file count. Active overall progress is marked `~`: equal workflow-step weights plus measured partial worker work or source-hash bytes, not elapsed-time prediction. Nested child actions contribute once through their parent file. Requested replacements reserve 15% of estimated work until replacement checks finish; active coordinators never report 100%. Failed and skipped files remain resolved work, not successful conversions.

Recovery inventory lists owned artifacts currently present on disk, with the last recorded error. Final-checkpoint cleanup retains all library, SHA-256 and ownership checks. A separate `transcode_backups(mode=discard_duplicate)` can discard redundant owned recovery artifacts from a failed promotion only while its unchanged original and full backup match the recorded digest, no delete/publication intent exists, and all recorded library commands resolved. It claims the original action's execution lease, repeats no conversion/import/rename/rescan, preserves failed status/checkpoint/error, and does not count a successful replacement or realized savings. Equal sizes only enable verification; they never authorize deletion. `transcode_backups(mode=restore)` (**Move original back**, shown when `restore_available`) puts an original that a cancelled or failed same-name replacement left at its recovery path back at its library path: only while that path is empty, after checking the file against the recorded SHA-256 (a full read, unless its file identity is unchanged since this process verified it), with a no-replace rename. It applies to same-name filesystem promotions only. If another file takes the library path first, the rename is refused, nothing moves and the offer goes away. It deletes nothing and resumes no workflow.

Cleanup publishes durable phases and byte observations, at most once per second while hashing. Clients poll them while the cleanup HTTP request is still pending, retain the lock on a lost response with ongoing observations, and show the terminal result. The confirmation groups file, removable bytes and collapsed locations; the actual outcome may retain the copy on verification failure.

Queue accounting rereads authoritative SQLite rows but memoizes bounded JSON projections. Complete input/output/state strings are compared before reuse, including same-size writes in the same timestamp; status, checkpoints and metadata are always fresh. The memo has a 64 MiB limit and drops removed rows. Full action history remains unchanged. Independent queue/detail/worker/cleanup refreshes run together.

Candidate validation review offers acceptance, rejection (keep original), deferral and a new configuration for the reviewed batch file only. Sizes and filename come from that child, not aggregate batch totals. Decisions bind to the exact durable candidate version under the execution lease. Reconfiguration first validates settings/readiness, rejects that candidate, then admits one frozen-file attempt with a stable receipt; other batch items are excluded and replacement approval is not inherited.

Recovery inventory also offers explicit Remove copy for finished jobs. This removes only owned regular backup/partial artifacts without checking the replacement or replaying promotion, and retains job history. A concise irreversible-removal confirmation is required; active jobs, symlinks and altered ownership remain blocked. Verify & clean up remains an independent alternative.


### Goal advice for the chosen file

`GET /api/maintenance/source-profile?path=...` backs the "Process videos" goal step. It resolves the path against the same read allow-list as `GET /api/maintenance/folder` (anything else is a 400), accepts only a regular video file, and reads it with the shared ffprobe inspection under a six second budget, two reads at a time. It returns the file's resolution class, dynamic range, video codec, bit depth and size; for each goal (`size`, `compact`, `quality`, `x265_preserve`) a verdict of `ok`, `skip` (with the job's own `reason_code`) or `unknown` when a gate needs evidence the preview could not collect; and a `recommended` goal. The verdicts come from the gate functions `transcode_media` runs in preflight, so the form and the job cannot disagree. The goal form preselects the recommendation until the user picks a goal, marks goals that would skip, and asks before queueing one. A probe that fails answers 422 (408 on timeout, 429 when busy) and the form then shows the goals unchanged. The endpoint queues and writes nothing.

`GET /api/maintenance/source-tracks?path=...[&keep_languages=eng,spa]` backs the track picker in the same goal step. It resolves and reads the file exactly like `source-profile` (same allow-list, same two-slot read channel, so it answers 429 when busy) and returns its audio and subtitle tracks (`index`, `language`, `title`, `codec`, `channels`, `default`, `forced`, `original`) with a `keep` flag per track. The flags come from the same `SelectTracks` rules the job applies, using the saved languages or the `keep_languages` given (an empty value means every track), so the pre-checked boxes and an automatic job cannot disagree. The goal form sends `keep_audio_streams` and `keep_subtitle_streams` only when the user changed a box, and keeps at least one audio track unless the file has none, in which case only the subtitle list is sent. The goal form reads a file's profile first and its tracks after, so one file selection holds one read slot at a time. The endpoint writes nothing.

In Settings, the Transcode node block shows *x265 at a time* below the parallel jobs when the worker reports an x265 pool: *No limit* (the default) or *1*, saved with Apply to `POST /api/maintenance/worker-slots` as `x265_slots` together with the video/podcast split the worker runs. A request that leaves `x265_slots` out keeps the stored value, so the parallel jobs and split forms never change it; a value above the video slots (or the parallel jobs when slots are shared) is a 400, a value for a worker that does not report the pool is a 409, and lowering the parallel jobs below the limit clears it with a note. With *1*, a VideoToolbox encode can run beside one x265 encode on a node set to 2 parallel jobs; the slot usage line then reads `x265 1/1 · Ceiling 2`. The row is hidden for a worker that predates it and, on a node with one parallel job, until a limit is set. With several workers the server's per-worker `max_parallel_jobs` must be 0 or at least 2 for a second job to be assigned to a node, and with two nodes a second x265 job can wait on one node while the other's x265 slot is free (see [x265 at a time](transcode/TRANSCODING.md#x265-at-a-time)).

Settings has a Languages to keep editor next to the node's parallel jobs. It edits a draft of `GET/PUT /api/maintenance/keep-languages` and saves it with Apply; Reset to default stages the default list and Turn off stages an empty one, which keeps every track. A saved change applies to jobs created afterwards. A finished Save space or Shrink job reports the tracks it kept and dropped in its details (`tracks_message` on every job and batch file row, the full `tracks` report only in the one job's details). When the report shows kept untagged tracks, Choose tracks reopens the goal form for that file with the picker open, and starts a new single-file job with explicit picks. The job's details carry the `goal` the job ran with (mode, size limit, encoder, height cap), and Choose tracks repeats it, together with the library the job was routed to. It is offered only for a job that produced a converted file that has not replaced the original yet (the original is still the source to re-encode), never for a skipped or not-converted one.

### Responsive controls and batch attempts

The browser submits media controls and recovery cleanup with `background:true` and a stable receipt key. HTTP returns a durable `maintenance_command` identifier immediately; the reconciler performs the work independently of the browser. `/api/maintenance/commands` exposes its pending/running/completed/failed state. Controls give immediate busy feedback, poll the receipt every second, and reuse it after a lost response. These receipts are excluded from the media queue and catalog. Synchronous MCP behavior is preserved.

`GET/POST /api/maintenance/batch-settings` changes scheduling intent within the existing batch coordinator. Scope is this reviewed candidate, unfinished files, or the full frozen file selection. It preserves the batch ID/number and original immutable inputs. Per-item settings, attempt generations and prior child actions are durable; item resets and the coordinator journal commit atomically under its execution lease. Active attempts finish before another attempt for that file is admitted. Reconfiguration does not delete candidates, expand the library selection, or reuse a replacement approval. Files with replacement jobs or an existing replacement review cannot be reconfigured through this route. Old API clients may still explicitly request a separate batch via the legacy batch-reconfigure route.

Queue outcomes distinguish skipped conversion, a candidate rejected by the user, and a technical failure. The engine's durable failed state for a rejected child remains unchanged; the UI projects `rejected_count` from the full batch relation, independently of the two example reasons shown in the queue. Finished batches show result counts and candidate availability instead of a 100% progress indicator. Details retain actual completed, failed and unperformed stages; skipped conversion and unrequested replacement never appear as successful work. Active workflow estimates still include resolved files, including rejections.

`Preview selection` inspects eligibility without encoding; `Create candidate` starts the conversion workflow and preserves originals. A goal has format limits and can skip files; an explicit profile is a different encoding intent. Reconfiguration of an all-skipped selection opens the full saved selection rather than an empty unfinished subset. Skips for unsupported sources require a different goal or an explicit profile in both the form and the API, preventing a repeat of the known unsupported intent. The settings form keeps file lists and optional savings/growth limits collapsed, and retains the same batch and prior attempts.

Settings review reads the current per-file limit overrides. Uniform selections display the current value; mixed selections display `Different per file`. `preserve_limits`, or the individual `preserve_savings` / `preserve_growth` flags, omit those overrides from the revision so a profile-only change or a change to one limit preserves the other current values. Explicitly edited blank fields still request defaults. Single-file batch rows identify the episode instead of repeating the season title, and candidate-ready results remain distinct from completed library replacement.


Settings submission uses only fields accepted by the batch-settings API; the obsolete quality-intent field is absent. Review shows the saved profile distribution and the selected profile’s encoder, quality/bitrate, preset, audio mode and container. Per-file details show the requested profile, including settings waiting for an active attempt to finish. A validation decision shows its actual stop reason instead of a worker progress bar; batch pauses and replacement approval are distinct. Command receipts distinguish queued requests from commands currently applying, without assuming a pending command is waiting for a media step.

Workflow filters use Finished for all terminal outcomes; Failed includes failed batch items even when their coordinator completed, and excludes deliberate candidate rejection. Batch savings exclude children explicitly recorded as previous attempts, including legacy child keys. Profile review identifies optimization-enabled profiles from the removed sample search; new jobs refuse them.

- **Job details.** The detail is one dialog with one anatomy, whatever the job and state: a sticky *header* (title, copy path, close), a *status* block (one chip, one progress headline with its bar, one step line, the counts and facts, each said once), the *files* of a batch, the collapsed *details* (plan, steps, costs, path, log) and a sticky *action bar* with at most two buttons and a *More* menu. At 640 px and below it is a full-screen sheet. A batch file is a single collapsed line: name, state and saving; opening it shows what it is doing, why it stopped, the tracks kept and its actions, with one primary action outlined in green. A state change redraws the same blocks in place; it never swaps one kind of detail for another, and an approved replacement closes its review and the job keeps showing its progress. *Where the time went* is only shown for a single file. The *Path* section names the worker that ran the job.

## Why Files is quick to page, and how to see where time goes

`GET /api/maintenance/library` and `GET /api/maintenance/folder` answer with a `Server-Timing` header (`arr`, `parse`, `list`, `readdir`, `entries`, `status`, `sizes`, `total`, in milliseconds; `arr;desc="cached"` when the *arr was not asked). Open the browser's network panel, or read the header in the iOS app, before guessing at a slow Files tab.

- The file-marks index is read once in the background when the server starts, so the first Files page after a deploy does not wait for it. After that it is refreshed as described above; a page opened after a minute of idle still waits for one read (`status` in `Server-Timing`, ~0.3 s per ten thousand files), because the marks are never shown older than that.
- Radarr and Sonarr only answer for a whole collection (hundreds of titles, several megabytes), so the server keeps the projected list per service for 45 seconds: paging, searching and sorting read memory. `refresh=1` on a library request asks the *arr again, and any POST to `/api/maintenance/*` drops the list. Per-title requests (`id=`) are not kept.
- When a NAS helper is configured and maps the folder, the listing is read by the helper (`POST /v1/list`) in one call that already carries every entry's type, size and time, so the SMB mount is not walked entry by entry. Without the helper, with an older helper, an unreachable one or more than 5000 entries, the folder is listed through the mount as before (`Server-Timing: list;desc="helper"` or `"mount"` says which). Links are always followed through the mount, since the read roots decide where they may lead. A folder with a name that is not valid UTF-8 is also listed through the mount, since JSON cannot carry that name. Sizes and times then come from the NAS disk itself, so they can differ by rounding from what SMB reports; the listing's `ETag` follows whichever source answered.
- A folder listing stats only the entries of the page it returns when ordered by name (with the mount; the helper's answer needs no stat). Size orders still need every entry's size, and are frozen in a `listing` so later pages do not repeat the work. A link is followed (and refused when it leaves the read roots) as before; an entry that is not a link is stat'ed once.

- `GET /api/maintenance/library?service=radarr|sonarr&view=index` returns every title in one answer for a client that holds the list and pages, searches and orders it itself: `{items, total, service, view: "index"}`, each item `id, title, year, path, size, episodeCount, hasFile, seriesType, metadata_source` plus `nav_status` when a batch touched it. `q` and `sort` still apply; the paged form (`offset`, `limit`, `has_more`, `season_groups`) is unchanged for older clients.
- `library` and `folder` answers carry a weak `ETag`, a hash of the exact body (marks and sizes included). Send it back as `If-None-Match`: unchanged is `304` with no body. Responses stay `Cache-Control: no-store`, so the client keeps the tag and body itself. The server keeps no extra state for this.

The larger design for an index with change tokens, and what the NAS helper can and cannot hold, is in [files-index-design.md](files-index-design.md).
